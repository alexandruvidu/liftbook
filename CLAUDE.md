# Liftbook — project rules

Liftbook is an original, offline-first gym workout tracker for iOS.

## Environment
- The owner develops on Windows with no Mac. **All building and testing happens
  on GitHub Actions** (`.github/workflows/ios.yml`). Never assume a local Xcode.
- The repo is **public**. The app is sideloaded unsigned with SideStore /
  LiveContainer. **Never add signing, certificates, provisioning profiles, or
  secrets.**

## Originality
- This is an original app. Do not use names, logos, icons, UI copy or
  screenshots from any existing commercial app.
- Exercise animations come from the ExerciseDB V1 dataset: the owner chose
  to bundle them into the IPA. They are fetched by CI at build time
  (`scripts/fetch_exercise_gifs.py`, IDs in
  `Liftbook/Resources/exercise-animations.json`) and never committed.
- Write all text, exercise descriptions, and designs from scratch.

## Stack
- Swift 6, SwiftUI, SwiftData, Swift Charts. No third-party dependencies unless
  truly needed.
- Deployment target iOS 18; built with the latest stable Xcode on CI.
- The Xcode project is generated by XcodeGen from `project.yml`. **Never commit
  an `.xcodeproj`.**
- Folders:
  - `Liftbook/Features/<Feature>/` — views and view logic per feature
    (Activity, Machines and Media included); shared building blocks
    (`Block`, `BlockSection`, pill buttons) are in `Features/Shared/Blocks.swift`
  - `Liftbook/Models/` — SwiftData models and domain logic
  - `Liftbook/Resources/` — assets, bundled JSON
  - `LiftbookTests/` — unit tests (Swift Testing)
  - `LiftbookUITests/` — UI tests; use `snap("<name>")` from `Snapshot.swift`

## Screenshots
- `snap("<name>")` attaches a screenshot to the test result and, on CI, writes
  `screenshots/<name>.png` (via `TEST_RUNNER_SCREENSHOT_DIR`). CI fails if no
  screenshots are produced; they are uploaded as the `screenshots` artifact.
- Name screenshots `<feature>-<light|dark>` (kebab-case), e.g.
  `exercise-list-dark`.
- Force an appearance by launching with
  `app.launchArguments += ["-uiTestAppearance", "dark"]` (or `"light"`).
- Launch the app in UI tests with `XCUIApplication.launchLiftbook(appearance:)`
  (`LiftbookUITests/AppLauncher.swift`): it forces the appearance and uses a
  fresh in-memory SwiftData store, so tests never share data.
- UI tests run on one pre-booted simulator (parallel clones timed out on CI).
  Only the classes in `ci/ui-tests.txt` run per push (`ALL` runs everything;
  so does a manual workflow run with "full" checked);
  keep screenshot names unique and tests independent of each other.
- Review every new screenshot in both appearances before ticking an item.

## UI test helpers and pitfalls
- `LiftbookUITests/UITestHelpers.swift`: `field.enter(text)` (waits for
  keyboard focus), `app.dismissKeyboard()`, `button.openMenu(showing:)`,
  `app.scrollTo(element)`, `app.finishWorkout()` (Finish + summary Done),
  `app.openTab("Home"|"Exercises"|"Activity"|"Profile"|"Start")`,
  `app.startEmptyWorkout()`, `app.runningBar` (shown while a workout runs).
- `launchLiftbook(seedSampleData:seedHistory:seedPhotos:)` seeds an
  "Upper Body" routine, three finished workouts (1, 2 and 9 days ago) and
  two drawn progress photos (the system photo picker can't be scripted).
- `launchLiftbook(seedMachines:)` adds bench press machines "Flat bench A",
  "Flat bench B" and "Smith" with drawn photos and a workout on A (50 kg × 10);
  `seedMedia:` adds two drawn photos of your own to bench press. UI tests
  never download exercise images from the network.
- Elements inside a `Button` (e.g. an exercise header) aren't separately
  visible to UI tests; read the button's `label` instead.
- `launchLiftbook(storeFile:)` keeps data in a temporary file so a test can
  quit and relaunch the app; settings (`@AppStorage`) start empty on each
  UI-test launch.
- Never key SwiftUI views (`ForEach` ids, `sheet(item:)`) on a new model's
  `persistentModelID`: it changes on the first save and rebuilds the view
  (menus close, fields lose focus). Save right after inserting, and use a
  UUID or `ObjectIdentifier`.
- Avoid per-second `TimelineView`s in screens with menus or text fields; use
  `Text(date, style: .timer)` / `ProgressView(timerInterval:)`.

## Workflow for every PLAN.md item
1. Take the first unchecked item in `PLAN.md`; implement it in small, focused
   changes.
2. Add unit tests for logic, and a UI test that navigates to the feature and
   calls `snap("<feature-name>")`. Add accessibility identifiers so UI tests
   can find elements.
3. List the UI test classes for this item (new ones and any whose screens you
   changed) in `ci/ui-tests.txt`; CI runs all unit tests but only those UI
   tests, to keep runs short. Commit with a clear message, push, and follow
   the `ci-loop` skill
   (`.claude/skills/ci-loop/SKILL.md`) until CI is green and screenshots look
   right.
4. Tick the item in `PLAN.md`, commit, push, move to the next.
5. An item is done only when CI builds, all tests pass, and its screenshot
   looks correct.

## Stopping rules
- If the same item fails CI 3 times in a row, stop: write what you tried and
  the error into `BLOCKED.md`, commit it, and end.
- At the end of each phase, set `ci/ui-tests.txt` to `ALL` so the full UI
  suite runs, and fix anything it finds before the summary.
- Stop at the end of each phase and give a short summary so the owner can test
  the IPA (the `ipa` artifact) on their iPhone.
- About every 10 items, do a cleanup pass: remove dead code, split files over
  ~200 lines, keep naming consistent.

## Out of scope
Social feed, followers, cloud sync, accounts.
