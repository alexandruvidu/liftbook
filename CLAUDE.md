# Liftbook — project rules

Liftbook is an original, offline-first gym workout tracker for iOS.

## Environment
- Development happens on a Mac with Xcode and an iOS simulator. **All building
  and testing happens locally** (`scripts/test.sh`, see the `local-test`
  skill). GitHub Actions (`.github/workflows/ios.yml`) only builds the IPA and
  publishes it; it runs no tests.
- The repo is **public**. The app is sideloaded unsigned with SideStore /
  LiveContainer. **Never add signing, certificates, provisioning profiles, or
  secrets.**

## Originality
- This is an original app. Do not use names, logos, icons, UI copy or
  screenshots from any existing commercial app.
- Exercise pictures are bundled into the IPA, fetched by CI at build time
  (`scripts/fetch_exercise_art.py` into `Resources/ExerciseArt`) and never
  committed: RepDB free-tier illustrations (start/peak poses, IDs in
  `Liftbook/Resources/exercise-illustrations.json`; their license requires
  the visible "Exercise data by RepDB (repdb.co)" link in Profile and
  forbids republishing the files), and ExerciseDB V1 GIFs only for the
  exercises RepDB doesn't cover (`exercise-animations.json`).
- The exercise catalog is the hand-written `Resources/exercises.json` (its
  IDs never change: workouts point at them) plus `exercises-more.json`,
  merged by `scripts/build_catalog.py` from ExerciseDB, RepDB,
  free-exercise-db and wger. The owner chose to use the source databases'
  descriptions there; RepDB text is added by CI at build time
  (`ExerciseArt/repdb-descriptions.json`), never committed. Unit tests that
  need exact results use `ExerciseLibrary.handWritten`.
- Write all other text and designs from scratch.

## Stack
- Swift 6, SwiftUI, SwiftData, Swift Charts. No third-party dependencies unless
  truly needed.
- Deployment target iOS 26; built with the latest stable Xcode. iOS 27
  APIs stay behind `#available`.
- The Xcode project is generated by XcodeGen from `project.yml`. **Never commit
  an `.xcodeproj`.**
- Folders:
  - `Liftbook/Features/<Feature>/` — views and view logic per feature
    (Activity, Machines and Media included); shared building blocks
    (`Block`, the concentric `.card` shape) are in `Features/Shared/Blocks.swift`
  - `Liftbook/Models/` — SwiftData models and domain logic
  - `Liftbook/Resources/` — assets, bundled JSON
  - `LiftbookTests/` — unit tests (Swift Testing)
  - `LiftbookUITests/` — UI tests

## UI conventions
- List-like screens use `List`/`Form` sections; custom `Block` cards only for
  rich content (live-workout exercises, photo grids, machine cards).
- Buttons use the system `.glass` style; the one main action per screen uses
  `.prominentGlassButton()` (`Shared/BrandColors.swift`), never a bare
  `.glassProminent`: the system keeps that label white, unreadable on the
  dark-mode mint accent. In toolbars, also set the color on the label's `Text`.
- Start Workout and the running workout live in the tab bar's bottom accessory.

## Testing
- Test locally before **every** commit: `scripts/test.sh` runs the unit tests,
  `scripts/test.sh <UITestClass> ...` adds UI test classes, `scripts/test.sh all`
  runs everything. Never commit code that hasn't passed.
- Check changed screens yourself in the simulator (the `device-interaction`
  skill), in light and dark mode. No screenshot artifacts are needed.
- Force an appearance by launching with
  `app.launchArguments += ["-uiTestAppearance", "dark"]` (or `"light"`).
- Launch the app in UI tests with `XCUIApplication.launchLiftbook(appearance:)`
  (`LiftbookUITests/AppLauncher.swift`): it forces the appearance and uses a
  fresh in-memory SwiftData store, so tests never share data.
- UI tests run on one simulator, not in parallel; keep tests independent of
  each other.

## UI test helpers and pitfalls
- `LiftbookUITests/UITestHelpers.swift`: `field.enter(text)` (waits for
  keyboard focus), `app.dismissKeyboard()`, `button.openMenu(showing:)`,
  `app.scrollTo(element)`, `app.finishWorkout()` (Finish + summary Done),
  `app.openTab("Home"|"Exercises"|"Activity"|"Profile"|"Start")`,
  `app.startEmptyWorkout()`, `app.runningBar` (shown while a workout runs).
- `launchLiftbook(seedSampleData:seedHistory:seedPhotos:)` seeds an
  "Upper Body" routine, three finished workouts (1, 2 and 9 days ago) and
  two drawn progress photos (the system photo picker can't be scripted).
- `launchLiftbook(seedMachines:)` adds bench press machines "Flat bench A",
  "Flat bench B" and "Smith" with drawn photos and a workout on A (50 kg × 10);
  `seedMedia:` adds two drawn photos of your own to bench press. UI tests
  never download exercise images from the network.
- Elements inside a `Button` (e.g. an exercise header) aren't separately
  visible to UI tests; read the button's `label` instead.
- `launchLiftbook(storeFile:)` keeps data in a temporary file so a test can
  quit and relaunch the app; settings (`@AppStorage`) start empty on each
  UI-test launch.
- Never key SwiftUI views (`ForEach` ids, `sheet(item:)`) on a new model's
  `persistentModelID`: it changes on the first save and rebuilds the view
  (menus close, fields lose focus). Save right after inserting, and use a
  UUID or `ObjectIdentifier`.
- Avoid per-second `TimelineView`s in screens with menus or text fields; use
  `Text(date, style: .timer)` / `ProgressView(timerInterval:)`.

## Workflow for every PLAN.md item
1. Take the first unchecked item in `PLAN.md`; implement it in small, focused
   changes.
2. Add unit tests for logic, and a UI test that navigates to the feature. Add
   accessibility identifiers so UI tests can find elements.
3. Follow the `local-test` skill (`.claude/skills/local-test/SKILL.md`): run
   the unit tests and the UI test classes for this item (new ones and any
   whose screens you changed), and check the screens in the simulator. Then
   commit with a clear message, push, and confirm the CI IPA build succeeds.
4. Tick the item in `PLAN.md`, commit, push, move to the next.
5. An item is done only when all tests pass locally, its screens look right in
   the simulator, and CI builds the IPA.

## Stopping rules
- If the same item fails its tests 3 times in a row, stop: write what you tried and
  the error into `BLOCKED.md`, commit it, and end.
- At the end of each phase, run the full UI suite (`scripts/test.sh all`) and
  fix anything it finds before the summary.
- Stop at the end of each phase and give a short summary so the owner can test
  the IPA (the `ipa` artifact) on their iPhone.
- About every 10 items, do a cleanup pass: remove dead code, split files over
  ~200 lines, keep naming consistent.

## Out of scope
Social feed, followers, cloud sync, accounts.
